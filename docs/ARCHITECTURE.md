# Architecture

FedLeave is one distribution containing a command-line application, two Qt
applications, report renderers, and compatibility entry points. Importable
Python code lives under `src/`; repository-root directories contain project
metadata, documentation, tests, assets, installers, and build orchestration.

## Source map

- `src/fedleave/` owns leave-year data, validation, calculations, storage, and
  the Typer command application. `fedleave.commands` contains command adapters;
  calculation and persistence code remains independently callable below it.
- `src/fedleave/mcp/` discovers the CLI registry, generates tool schemas, enforces
  trusted launch-time policies, and invokes the sibling CLI through stdio MCP.
  It uses the official Python MCP SDK and contains no leave calculations.
- `src/fedleave_gui/` owns the calendar GUI and its subprocess adapter to the
  `fedleave` command. It does not duplicate leave calculations.
- `src/fedleave_analytics/` owns read-only analytics calculations and their Qt
  presentation.
- `src/*_chart/`, `src/yearly_leave_comparison_chart/`, and
  `src/fedleave_month_report_graphic/` are maintained compatibility packages
  for the published companion commands.
- `scripts/lib/common/application_manifest.toml` is the authoritative map from
  `pyproject.toml` console commands to PyInstaller settings.
- `installer/` packages and installs validated bundles; it does not contain
  application behavior.

## Dependency direction

The core `fedleave` package must not import a GUI package. GUI and report
packages may call or import core code. Installer and build code discovers
application entry points from `pyproject.toml` instead of maintaining another
command list. Runtime, optional, test, and build dependencies are likewise
declared only in `pyproject.toml`.

The GUI normally invokes the CLI through its sibling `fedleave` executable.
This keeps the packaged applications consistent with direct CLI use and makes
the subprocess boundary explicit. Executable discovery checks the active
interpreter or bundle directory before `PATH`.

CLI leaf invocations hold a per-datastore OS file lock for their entire
read/modify/write cycle. Reads use an existing shared lock without creating coordination files. Startup never migrates data.
This coordinates standalone CLI processes, GUI backend subprocesses, and MCP
CLI children without transferring locks between parent and child processes.
Direct importers of the storage/calculation APIs must acquire `datastore_lock`
around their own transactions; an atomic JSON replacement alone is insufficient.

## Compatibility policy

Existing console command names, module names, JSON shapes, data files, and
installer behavior are public compatibility surfaces. Structural work should
preserve them unless a separately reviewed change provides a migration path.
In particular, the companion package names remain top-level packages even
though all of their source now shares the `src/` tree.

New extraction work should follow cohesive behavior boundaries backed by
characterization tests. File length alone is not a reason to introduce a
service, repository, controller, or wrapper.

## Cross-year accounting

`categories.py` is the canonical registry for carryover, lot and activity policy.
`cross_year.py` owns pure manual/carryover plans, canonical source/policy hashes,
explicit ancestry resolution, and generated-record reconciliation. Manual years
stop ancestry traversal. Legacy years without metadata have unknown lineage;
ordinary reads never infer a predecessor from directory contents.

`cli_helpers.load_read_snapshot` returns an operation-local JSON-compatible
snapshot with configuration/warnings as nonpersisted attributes. `snapshot --json`
provides the same state to companion processes, with transient `snapshot_rules`.
Resolve an ancestry chain once per operation and reuse the result for chart
points. Reports synthesize accruals and expiration events on copies. No read
persists migration, caches or disposal records. Mutation loaders retain raw
lineage so unrelated edits cannot implicitly reconcile a stale destination.

Opening metadata is authoritative when mirrored legacy starting transactions
exist. Carried lots use stable origin year/ID and deterministic destination IDs,
original amount/date/deadline/extensions, remaining hours and predecessor chain.
FIFO links generated by the expiration engine can be re-resolved; explicit
legacy/user lot links remain authoritative and invalid links report conflicts.
Deadlines are inclusive, with disposal effective the next day.

The CLI is the sole canonical ledger writer. Creation atomically creates only
the destination, refuses replacement and leaves the source untouched. Apply
rechecks reviewed source/target/policy fingerprints under the datastore writer
lock. Reconciliation previews the whole dependent chain, changes only generated
openings/lots and preserves genuine destination activity. Backups precede a
recoverable journal; errors roll back where possible, and interrupted work
requires explicit `carryover-reconcile --recover`. Per-file atomic replacement
is not represented as multi-file atomicity.
